# Prisma Migration Flow — Voyra Tour Bali

> How schema changes flow from `schema.prisma` → migration SQL → Contabo Postgres → Vercel runtime.

## 1. Day-1 deploy (already done — for reference)

The first migration run against the fresh Contabo DB applied 37 historical migrations:

```bash
npx prisma generate
npx prisma migrate deploy        # uses DIRECT_URL = voyra_admin
npx prisma db seed               # uses DATABASE_URL = voyra_app (DML-only seed)
```

```bash
  -c "SELECT COUNT(*) FROM _prisma_migrations WHERE finished_at IS NOT NULL;"

```

## 2. Day-2 schema change (the normal flow)

When you change `prisma/schema.prisma`:

```bash
# 1. Edit schema.prisma

# 2. Generate the new migration locally — runs against the live Contabo DB
#    via DIRECT_URL = voyra_admin (admin role required for DDL).
npx prisma migrate dev --name descriptive_change_name

# 3. Review the generated SQL under prisma/migrations/<timestamp>_<name>/migration.sql
#    Look for:
#      - destructive ops (DROP COLUMN, DROP TABLE)  → may need data migration
#      - non-idempotent ops (DROP TABLE without IF EXISTS) → consider hardening
#      - long-running ops (CREATE INDEX without CONCURRENTLY) → consider locking risk

# 4. Commit:
git add prisma/schema.prisma prisma/migrations/<timestamp>_*
git commit -m "feat(db): <change>"

# 5. Push, open PR, merge to master

# 6. After Vercel deploy succeeds (build runs `prisma generate`),
#    the migration is ALREADY applied to Contabo because step 2 wrote it.
#    To apply to a separate prod DB (if you ever fork prod from dev), use:
npx prisma migrate deploy
```

> Why `prisma migrate dev` writes directly to Contabo today: we have **one** environment. Once a separate `voyra_bali_dev` DB is provisioned, dev work moves there and `migrate deploy` becomes the production gate.

## 3. The idempotency fix from Day-1

When applying the historical migration set to the fresh Contabo DB, two migrations failed because they referenced objects that didn't exist on a fresh DB but existed on the original Prisma Cloud DB.

### 3.1 The problem

`prisma/migrations/20260506022349_drop_email_campaign_add_ledger_index/migration.sql` originally was:

```sql
DROP TABLE "EmailCampaign";
CREATE INDEX "AiCreditLedger_reservationStatus_settledAt_idx"
  ON "AiCreditLedger"("reservationStatus", "settledAt");
```

Failed twice on a fresh DB:
1. `EmailCampaign` doesn't exist yet (the migration that creates it is later in the chain — chronological mistake in the original repo).
2. `AiCreditLedger` is created by `20260511000000_add_ai_subscription_and_credits` — chronologically *after* this index attempt.

### 3.2 The fix

`migration.sql` was rewritten to be idempotent:

```sql
-- DropTable
DROP TABLE IF EXISTS "EmailCampaign";

-- CreateIndex (deferred — table created later on fresh DBs)
DO $$
BEGIN
  IF EXISTS (
    SELECT 1 FROM information_schema.tables
    WHERE table_schema = 'public' AND table_name = 'AiCreditLedger'
  ) THEN
    CREATE INDEX IF NOT EXISTS "AiCreditLedger_reservationStatus_settledAt_idx"
      ON "AiCreditLedger"("reservationStatus", "settledAt");
  END IF;
END $$;
```

And the index was appended to `20260511000000_add_ai_subscription_and_credits/migration.sql` so it actually gets created on fresh DBs after the table exists:

```sql
-- CreateIndex (originally from 20260506022349, deferred until table exists)
CREATE INDEX IF NOT EXISTS "AiCreditLedger_reservationStatus_settledAt_idx"
  ON "AiCreditLedger"("reservationStatus", "settledAt");
```

### 3.3 The recovery procedure (if you ever bootstrap another fresh DB)

```bash
# When migrate deploy errors with P3018 (migration partially applied):
npx prisma migrate resolve --rolled-back <migration_name>
# Fix the SQL idempotently, then:
npx prisma migrate deploy
```

> ⚠️ `--rolled-back` only flips the bookkeeping in `_prisma_migrations`. The **partial DDL effects** (rows already inserted, indexes already created) are not undone. Inspect the DB before retrying.

### 3.4 Rule for future migrations

Any migration generated by Prisma that contains:

- `DROP TABLE "X";` — change to `DROP TABLE IF EXISTS "X";` if `X` may not exist on a clean bootstrap
- `CREATE INDEX "I" ON "T"(...)` referencing a table from a later migration — wrap in `DO $$ ... IF EXISTS ... END $$` block

This is mainly relevant when **squashing** or **reordering** migrations historically. Greenfield migrations are fine as Prisma generates them.

## 4. Roles in the migration flow

| Step | Connection | Role |
|---|---|---|
| `prisma migrate dev` | `DIRECT_URL` | `voyra_admin` |
| `prisma migrate deploy` | `DIRECT_URL` | `voyra_admin` |
| `prisma migrate resolve` | `DIRECT_URL` | `voyra_admin` |
| `prisma migrate status` | `DIRECT_URL` | `voyra_admin` |
| `prisma db push` | `DIRECT_URL` | `voyra_admin` |
| `prisma db seed` | `DATABASE_URL` (script-level) | `voyra_app` (default) |
| `prisma studio` | `DATABASE_URL` | `voyra_app` (read/write within DML) |

`voyra_app` cannot run migrations even if you pointed `DIRECT_URL` at it — Postgres rejects the DDL. This is the intended safety net.

## 5. Schema drift checks

After deploy, verify schema and migrations match what's tracked:

```bash
npx prisma migrate status      # should say "Database schema is up to date"
npx prisma db pull --print     # introspect — diff against schema.prisma manually
```

Drift causes:
- Someone ran ad-hoc DDL via `psql` instead of a migration → bad
- A migration was edited *after* it was applied → bad (Prisma checksum mismatch warning)
- Provider-managed extensions / triggers (none in this repo today)

Fix drift by writing a new migration that aligns the schema, never by hand-editing `_prisma_migrations`.

## 6. Pre-merge checklist (per PR that touches schema)

- [ ] `prisma/schema.prisma` change is described in the PR body
- [ ] New migration file committed (don't squash into a previous migration)
- [ ] Migration SQL reviewed: no plain `DROP TABLE`, no plain `DROP COLUMN` without data backfill
- [ ] `npx prisma migrate status` clean
- [ ] `npm run build` passes (catches Prisma Client type drift)
- [ ] Backwards-compatible? If not, plan a two-step rollout (deploy code that tolerates both shapes → run migration → deploy code that uses the new shape).
